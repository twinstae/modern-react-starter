# 회고 기록

티켓마다 **작업 환경**을 개선한 것을 남긴다. 구현 버그 하나는 티켓의 "작업하며 배운 것"에
남기고, 여기서는 같은 부류가 다시 나오지 않게 만든 구조만 다룬다.

## 회고 방식

매 티켓 뒤 아래 일곱 범주를 **모두** 훑는다. 문제가 없는 범주도 "없음"이라고 적어,
훑었다는 사실을 남긴다. 대책은 문서가 아니라 **파일·명령·테스트·훅 중 하나**로 적는다.

1. **Navigation** — 파일을 찾기 어려웠나? 숨은 의존성이 있었나? 진입점 문서가 있나?
2. **Automated checks** — 놓친 실수를 잡을 lint/type/test/훅이 있나? 이미 있는 검사가
   연결되지 않은 채 방치됐나?
3. **Coding standards** — 리뷰어가 반복해서 지적할 판단 기준이 있나? 기계적으로 막을 수
   있는 것은 lint/타입/테스트로, 판단이 필요한 것만 글로 남긴다.
4. **Global AGENTS.md** — 전역 지침이 비대해졌나? 앱별 진입점이 없어 매번 프롬프트에
   의존하나?
5. **Tool economy** — 같은 문서를 반복해서 받거나, 비싼 탐색을 반복하나?
6. **No-ops** — 지침이 실제 행동을 바꾸지 않나? 지켜지지 않는 규칙은 없나?
7. **Information access** — 실행 로그·시드·재현 절차에 접근하기 어려웠나?

같은 증상이 두 번 나오면 구조로 막는다. 한 번만 난 구체적 실수는 여기 쓰지 않는다.

## 00001 — 앱 뼈대

**관찰**

- 루트 `bun run ci`가 book-curator와 무관한 `simple-event` 타입 오류와 `solo-quest` lint
  오류로 실패한다. 티켓 인수 조건을 앱 밖의 실패가 막았다.
- 에이전트가 앱 단독 dev/Storybook 확인은 잘했지만, "루트 dev"와 "앱 단독 dev"의 차이를
  스스로 판단해 기록해야 했다. 포트와 확인 방법을 더 명시할 필요가 있었다.
- Vite+ type-aware lint, Storybook 10 viewport, fast-check v4 함정은 티켓 문서에 없었다.
  해결책은 티켓의 "작업하며 배운 것"에만 남아 다음 에이전트가 다시 만날 수 있었다.

**반영**

- `apps/book-curator`에 `check` 스크립트를 더했다. 루트 CI 대신 앱 범위 lint·format·
  typecheck·test를 한 번에 돌리는 커밋 전 게이트다.
- playbook에 루트 CI를 쓰지 않는 이유와 `storybook-static`을 커밋하지 않는 규칙을 적었다.
- 다음 회고 때 확인할 것: 에이전트가 `check`를 실제로 돌렸는지, 루트 CI 실패를 다시
  조사하느라 시간을 썼는지.

## 00002 — 큐레이션 코어

**관찰**

- `check` 게이트를 실제로 썼고, 루트 CI를 다시 조사하지 않았다. 00001의 개선이 먹혔다.
- 코어가 7개 파일로 늘었지만 다음 티켓이 함수 이름·오류·0점 규칙을 파일마다 다시
  찾아야 한다. 티켓 문서의 "작업하며 배운 것"은 구현자에게는 남지만 다음 에이전트의
  진입점은 아니다.
- 테스트 46개 중 컴포넌트는 1개뿐이다. 순수 계산을 컴포넌트로 올리지 않은 판단은 좋았다.

**반영**

- playbook에 "이미 있는 코어" 절을 더해 공개 함수, 오류, 0점·5의 수·비슷함 규칙을
  한곳에 적었다. 다음 티켓은 파일을 다시 읽지 않고 여기서 시작한다.
- 다음 회고 때 확인할 것: 다음 에이전트가 기존 코어를 다시 만들거나 이름을 바꾸지
  않는지, 새 결정을 playbook에 반영해야 하는지.

## 00003 — 공개 점검기와 시드

**관찰**

- 사람이 정할 것(시드 문구, 기준 응답, 문항 수, 반대 문항, 동점 순서, 10~18% 기준)이
  `SEED-QUESTIONS.md`와 티켓 문서에 흩어졌다. 사용자가 돌아왔을 때 여러 파일을 읽어야 한다.
- 시드가 게이트를 통과했지만 B6가 17.9%로 상한에 붙어 있다. 다음 티켓이 문구나 순서를
  조금 바꾸면 바로 실패할 수 있다. 이 사실이 "작업하며 배운 것"에만 있었다.
- 에이전트가 스스로 playbook에 코어 진입점을 더했다(좋은 행동). 회고를 기다리지 않아도
  다음 사람이 읽을 곳을 남기는 습관은 유지한다.

**반영**

- `docs/OPEN-QUESTIONS.md`를 만들었다. 사람이 정할 것과 환경 이슈를 한곳에 모으고,
  세부 근거는 `SEED-QUESTIONS.md`를 가리킨다. playbook의 "막히면 여기에"와 연결했다.
- 다음 회고 때 확인할 것: 시드가 깨졌을 때 에이전트가 상수를 풀지 않고 결정 요청을
  남기는지, OPEN-QUESTIONS가 중복으로 불어나지 않는지.

## 00004 — 문장·조사·인용

**관찰**

- 티켓 본문의 `{drawer}이/가` 예시와 실제 문법 `{drawer:이/가}`가 달라 에이전트가
  한 번 멈췄다. playbook §5.1에 실제 문법이 적혀 있었지만, 티켓 예시가 더 강하게 읽힌다.
- 리뷰에서 별명에 "님"을 붙여 넣으면 "토끼 님 님"이 되는 것을 찾았다. 테스트는
  "템플릿에 님이 있을 때"만 봤고, "별명에 님이 있을 때"는 빠져 있었다.
- 인용은 긍정 기여만 쓴다. 선택형 가중치가 0·음수인 질문 세트에서는 인용이 없어
  `curate`가 실패할 수 있다. 이 결정은 코드에만 있고 사람이 확인할 목록에는 없었다.

**반영**

- `renderStatement`가 별명 끝의 "님"을 중복해서 붙이지 않게 고치고 테스트를 더했다.
  playbook §5.1에 "별명에 이미 님이 있으면 한 번만"을 적었다.
- `OPEN-QUESTIONS.md`에 문장 문구와 긍정 기여 인용 정책을 더했다.
- 다음 회고 때 확인할 것: 새 사용자 입력(별명·문구)이 들어오는 경계에서 정규화
  예시를 실제 입력으로 먼저 적는지, 티켓 예시와 playbook 문법이 어긋나지 않는지.

## 00005 — 서가와 저장소

**관찰**

- PGlite 테스트를 파일마다 새로 띄우면 느리고 메모리가 남는다는 것을 에이전트가
  solo-quest/qr-quest를 읽고 스스로 피했다. 이 지식이 playbook에는 없었다.
- 서랍 표시(`mark`)를 질문 세트에 넣으면서 시드 값이 `[가정]`이 되었는데, 사람이
  정할 목록에는 없었다.
- 계약 테스트를 하나만 만들고 메모리·PGlite가 함께 부른 것은 좋았다. TICKET-00008/00009가
  저장소를 더할 때 같은 실수를 반복하지 않게 명시할 가치가 있다.

**반영**

- playbook 도구 절에 PGlite 테스트 패턴(파일당 DB 하나, beforeEach truncate, 계약
  테스트 하나)을 적었다.
- `OPEN-QUESTIONS.md`에 서랍 표시 문구와 3종 미만 운영 경고 강도를 더했다.
- 다음 회고 때 확인할 것: 새 저장소가 계약 테스트를 공유하는지, PGlite를 테스트마다
  새로 띄우지 않는지.

## 00006 — 키오스크 흐름

**1. Navigation**

- 문제: 앱에 `AGENTS.md`가 없어, 작업 규칙이 매번 서브에이전트 프롬프트에만 있었다.
  `AGENT_PLAYBOOK.md`·`TECH_SPEC.md`·`RUNBOOK.md`의 관계도 프롬프트가 알려 줘야 했다.
- 대책: `apps/book-curator/AGENTS.md`를 짧은 진입점으로 두고, 플레이북·티켓·용어·
  실행 안내·열린 질문을 가리킨다.

**2. Automated checks**

- 문제: 앱 `check`는 잘 돌지만, 그것을 **강제하는 훅이나 CI가 없다.** 에이전트가
  프롬프트를 따르지 않으면 검사 없이 커밋된다. 루트 CI는 다른 앱 때문에 못 쓴다.
- 대책: `.githooks/pre-commit`을 더해 `apps/book-curator` 파일이 스테이징되면
  `bun run check`를 돌린다. `git config core.hooksPath .githooks`로 이 저장소에만 건다.
  검사가 실패하면 커밋이 막힌다.

**3. Coding standards**

- 문제: 손님용 DTO와 관리자용/도메인 값을 나누는 규칙이 플레이북 산문에만 있었다.
  T6에서 `baselines`·`mark`를 번들에서 빼는 mapper를 만들었지만, 다음 티켓이 도메인
  객체를 그대로 내보내도 막을 검사가 없다.
- 대책: 플레이북에 "손님 DTO는 도메인 객체를 펼치지 않고 명시적 mapper로 만들며,
  빠져야 할 필드의 부재를 API 테스트로 고정한다"를 규칙으로 남긴다. 타입/테스트로
  막을 수 있는 부분은 T7/T12의 API 테스트가 맡는다.

**4. Global AGENTS.md**

- 문제: 루트 `AGENTS.md`에는 Turborepo·Vite+ 생성 블록과 pstack 라우팅이 있어
  book-curator 작업과 무관한 지침이 섞여 있다.
- 대책: 전역을 줄이지 않고, 앱 `AGENTS.md`가 앱 규칙의 우선 진입점이 되게 했다.
  전역 파일은 생성 블록이라 직접 줄이면 다시 붙는다.

**5. Tool economy**

- 문제: 프런트 티켓마다 siheom SKILL/API를 원격에서 다시 받고, 긴 TECH_SPEC을 처음부터
  읽는다. 다만 실제로 두 번 이상 헤맨 흔적은 없었다.
- 대책: 없음. 플레이북 §5.1과 API 요약이 이미 탐색을 줄인다. 로컬 복사본을 만들면
  원본과 어긋날 위험이 더 크다.

**6. No-ops**

- 문제: "사람이 정할 일은 OPEN-QUESTIONS에"라는 규칙을 T5·T6 에이전트가 따르지 않았다.
  시드 표시·유휴 시간·글꼴이 `[가정]`으로 남았는데 목록에 없다.
- 대책: 앱 `AGENTS.md`와 플레이북에 "새 `[가정]` 값은 OPEN-QUESTIONS에 먼저"를 진입점
  수준으로 올리고, 이번 티켓의 항목을 실제로 더한다.

**7. Information access**

- 문제: 시드·개발 서버·Storybook·데이터 초기화·"준비 중"의 원인을 매 티켓이 다시
  조립해야 했다.
- 대책: `docs/RUNBOOK.md`에 처음 한 번, 개발, 확인, 초기화, 자주 막히는 곳을 적는다.

**다음 회고에서 확인할 것**

- 커밋 훅이 실제로 검사를 막는지(실패하는 변경으로 한 번 확인).
- 다음 에이전트가 앱 `AGENTS.md`만 읽고도 플레이북·티켓·실행 명령을 찾는지.
- 새 손님 DTO가 도메인 객체를 그대로 내보내지 않는지.

## 00007 — 결과 화면

**1. Navigation**

- 문제: 결과 카드에 "권하는 이유"가 필요해졌을 때, 그것이 서랍 데이터인지 책 데이터인지
  플레이북에 없었다. T7이 `Drawer.reason`을 새로 만들며 해결했지만, 다음 티켓이 다시
  서가를 결과 화면에 끌어올 수 있다.
- 대책: 플레이북 §5.2에 값별 소유 표를 넣었다. 질문 세트는 서랍 이름·문장·표시·이유,
  서가는 책 제목·책별 이유, 점수·코드는 내부 `Curation`만 소유한다.

**2. Automated checks**

- 문제: 시드 문항·표시·이유에 `[가정]` 접두어가 들어 있었고, T6 질문 화면과 T7 결과
  카드가 그것을 그대로 손님에게 보여 주었다. 화면 테스트는 "문구가 있다"만 봤지
  "편집 표시가 없다"를 보지 않았다.
- 대책: `seed-question-set.test.ts`가 모든 공개 문자열에서 `[가정]`/`TODO`/`TBD`를
  거부하고, `result-screen.test.tsx`도 `[가정]` 부재를 확인한다. 플레이북에 "편집
  표시는 문서에만"을 규칙으로 넣었다. 커밋 훅이 실제로 검사를 돌리는 것도 확인했다.

**3. Coding standards**

- 문제: "손님 DTO는 도메인 객체를 펼치지 않는다"는 지켜졌지만, 문자열의 성격(편집용
  표시 vs 손님 문구)을 나누는 기준이 없었다.
- 대책: 런타임 데이터에는 문장 자체만 넣고, 가정 표시는 `OPEN-QUESTIONS.md`·
  `SEED-QUESTIONS.md`에만 둔다. 이는 이제 테스트로 강제된다.

**4. Global AGENTS.md**

- 문제: 없음. 앱 `AGENTS.md`가 진입점으로 작동했고, 전역 파일은 그대로 두었다.

**5. Tool economy**

- 문제: 없음. 결과 스토리 8개를 손으로 쓰지 않고 시드와 `curate`로 생성해, 실제 출력과
  스토리가 어긋날 위험을 줄였다.

**6. No-ops**

- 문제: 없음. `OPEN-QUESTIONS`에 결과 문구·이유·표시를 실제로 더했고, 이전 티켓의
  "새 가정값은 여기에" 규칙이 처음으로 지켜졌다.

**7. Information access**

- 문제: 없음. `RUNBOOK.md`의 시드·개발 명령으로 화면을 띄울 수 있었다. 다만 시드에
  `[가정]`이 보인다는 사실은 실행해 보기 전까지 드러나지 않았다.
- 대책: 위 2번의 테스트가 실행 전에 잡는다.

**다음 회고에서 확인할 것**

- 새 손님 문자열의 출처마다 편집 표시 부재 검사가 붙는지.
- 결과·서랍 속 책 화면이 §5.2의 소유를 넘지 않는지.

## 00007 후속 — 디자인 리뷰

**1. Navigation**

- 문제: 화면을 고치는 사람이 볼 디자인 기준이 없었다. 색·글꼴·문구가 티켓마다 즉흥적으로
  정해졌고, 실제 가게 사진과 연결되지 않았다.
- 대책: `docs/DESIGN.md`에 실제 가게(초록 간판·노란 벽·종이·빨간 스탬프), 토스 라이팅
  원칙, warm editorial, NN/G 터치 타깃, 색·글자·문구·레이아웃 불변식을 모았다.
  앱 `AGENTS.md`가 이 문서를 가리킨다.

**2. Automated checks**

- 문제: `height: 100dvh` + `overflow: hidden` 때문에 결과 문장과 카드가 겹쳤는데,
  컴포넌트 테스트는 글자 존재만 봤고 레이아웃은 아무도 확인하지 않았다. “스타일 단언

- 문제: 수량 0인 책의 구매 기록, 2순위/다른 서랍 열쇠, 주인 모드 유휴 제한은 정책이
  정해지지 않았다. 코드가 임의로 정하면 현장과 어긋난다.
- 대책: `OPEN-QUESTIONS.md`에 C-3/C-5, 0수량, 유휴, 문구를 모았다. 지금의 동작(0은
  버튼 비활성, 10분 토큰)을 문서와 맞췄다.

**7. Information access**

- 문제: 주인 흐름을 실제로 따라가려면 PIN·열쇠·구매를 순서대로 눌러야 했다.
- 대책: RUNBOOK에 결과 → PIN → 주인 확인 → 열쇠 → 서랍 속 책 → 산 책 → 처음으로
  순서와 토큰 만료를 적었다.
