## 1. 무엇을 만드는가

> 책방에 온 사람이 태블릿의 질문에 답해 **"내가 지금 이런 질문 앞에 서 있구나"**를 알게 되고,
> 큐레이터의 이유와 함께 서랍 하나를 추천받아, 주인에게서 열쇠를 받아 책을 손으로 만난다.

가치는 책 제목이 아니라 **큐레이터의 문장**과 **서랍을 여는 순간**에 있다. 앱의 일은 그 순간까지 잘 데려다주는 것이다.

### MVP 범위

| 누가      | 무엇을                                                                                               | PRD      |
| --------- | ---------------------------------------------------------------------------------------------------- | -------- |
| 이용자    | 별명 → 질문에 답하고 되돌아가기 → 서랍 2개의 상태 + 추천 서랍 → 주인에게 보여 주기 → 서랍 속 책 안내 | UC-01~06 |
| 책방 주인 | 주인 확인(잠금) → 건넬 서랍과 서랍 속 책 → 실제로 건넨 서랍, (선택) 산 책 기록 → 처음으로            | UC-11    |
| 큐레이터  | 책 등록, 서랍마다 책과 수량                                                                          | UC-07~08 |
| 관리자    | 질문 세트(문항) 초안·복제·편집, 상태 문장, 공개 전 점검, 공개(버전)                                  | UC-09    |
| 시스템    | 익명 퍼널 이벤트, 학습 데이터가 되는 정답 표시                                                       | UC-10    |

큐레이터·관리자·주인은 MVP에서 한 역할(운영자)로 둔다(PRD 열린 질문 10).

### 범위 밖

- 온라인 비대면 흐름, 네이버 예약 연동, 결제(POS) 연동
- 학습 모델을 앱 안에서 학습시키기. MVP는 **학습 데이터를 쌓고 내보내는 데까지**, 학습과 비교는 TICKET-00013(v2)
- 결과 가져가기(카드 출력·QR), 오프라인 프로그램 안내, 형식·난이도 반영(PRD 열린 질문 6·7·9)
- 이벤트 대시보드. MVP는 DB에서 직접 읽는다

## 2. 도메인 모델

### 2.1 경계 (bounded context)

한 앱 안의 모듈 경계다. 서로 **id로만** 가리키고, 다른 경계의 내부 구조를 모른다.

```
 ┌─ 질문 세트 (authoring) ─────┐   ┌─ 서가 (shelf) ────────┐
 │ 서랍 7종의 이름·상태 문장    │   │ 책                     │
 │ 문항(서랍별) / 선택형 질문   │   │ 서랍 속 책과 수량       │
 │ 채점 방식(문항 평균 | 학습)  │   │                        │
 │ 초안 → 점검 → 공개 버전      │   └──────────┬─────────────┘
 └───────────┬────────────────┘              │ 지금의 서가
             │ 공개 버전(불변)                 │
             ▼                               ▼
        ┌─ 큐레이션 (engine, 순수 함수) ───────────────────┐
        │ 답 → 서랍 점수 → 순위 → 상태 문장 · 추천 서랍 · 인용 │
        └──────────────┬────────────────────────────────┘
                       ▼
   ┌─ 손님 차례 (kiosk) ──────────┐    ┌─ 기록 (analytics) ─────────┐
   │ 별명·진행을 탭 메모리에만     │───►│ 익명 퍼널 이벤트             │
   │ 주인 확인 잠금, 처음으로      │    │ 정답 표시(건넨 서랍, 산 책)  │
   └─────────────────────────────┘    └──────────────────────────┘
```

- **결과 = 서랍.** PRD v0.3 부록 B처럼 결과 7종이 곧 서랍 7개다. 질문 세트는 서랍의 "이름과 문장"을, 서가는 서랍의 "안에 든 책"을 안다. 둘은 서랍 코드(B1~B7)로만 만난다.
- 질문 세트는 책을 모른다. 서가는 질문을 모른다. "질문은 서랍을 찾고, 서랍은 큐레이터가 채운다."
- 손님 차례는 별명처럼 **저장하면 안 되는 것**을 한곳에 가둔다. 서버로 가는 길이 없다.

### 2.2 추천 알고리즘: 채점 방식은 데이터다

PRD 부록 A의 제안을 코드 구조로 옮긴다. 핵심은 **답을 서랍 점수로 바꾸는 방법을 공개 버전 안의 데이터로 둔다**는 것이다.

```
답 목록 ──► scorer(공개 버전.채점 방식) ──► 서랍 점수 ──► rank ──► 1·2순위
              ├ item-mean     (v1) 서랍별 문항 평균. 반대 문항은 6 - 답
              ├ choice-weight (v0.2 호환) 선택지별 서랍 가중치 합
              └ learned       (v2) 학습한 모델(예: 의사결정 나무)의 JSON
```

- 채점 방식이 바뀌어도 순위, 문장, 서랍, 화면, 이벤트, 점검기는 그대로다. 이것이 "여러 차례 학습해 새 버전으로 공개"를 가능하게 한다.
- 질문의 형식(문항형 1~5 / 선택형)과 채점 방식은 따로 정한다. MVP 시드는 문항형 + `item-mean`만 쓴다.
- 학습 모델도 공개 버전에 담긴 **불변 데이터**다. 같은 버전·같은 답이면 같은 결과다(I-2).
- 학습 데이터 = (버전, 답 목록, 추천 서랍, **주인이 건넨 서랍**, 산 책의 서랍). 모두 익명이다.

### 2.5 불변식

티켓마다 이 표의 id를 인수 조건에 인용한다.

| id   | 불변식                                                                                                                     | 검사                                                                |
| ---- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| I-1  | 공개된 질문 세트에서 **어떤** 답 목록이든 1순위와 2순위가 하나씩, 서로 다르게 정해진다                                     | 속성(무작위 질문 세트·답) + 공개 점검                               |
| I-2  | 같은 공개 버전에서 같은 답 목록은 같은 순위·상태 문장·추천 서랍을 낸다(채점 방식과 무관)                                   | 속성(결정성)                                                        |
| I-3  | 서랍 점수는 최종 답 목록만의 함수다. 되돌아가 답을 바꾸는 어떤 순서를 거쳐도 결과가 같다                                   | 속성(상호작용 무작위열)                                             |
| I-4  | 동점은 정해진 규칙으로만 깨지고, 규칙 끝까지 같으면 관리자가 정한 서랍 순서를 따른다(공개 점검이 그 비율을 보고)           | 예시 + 속성                                                         |
| I-5  | 질문 수·서랍별 문항 수·질문 형식은 질문 세트가 정한다. 코어와 화면 어디에도 "5개", "14개"가 없다                           | 속성(무작위 질문 세트)                                              |
| I-6  | 채점 방식이 무엇이든(`item-mean`/`choice-weight`/`learned`) 순위 이후의 계산과 화면은 같다                                 | 타입(공통 `DrawerScores`) + 속성                                    |
| I-7  | 서랍마다 서랍 속 책이 3종 이상이어야 공개(오픈)할 수 있다. 운영 중 깨지면 운영 화면과 주인 확인에 보인다                   | 공개 게이트 + 예시                                                  |
| I-8  | 권하는 이유마다 이용자가 실제로 한 답(그 서랍에 기여한 것)이 하나 이상 인용된다                                            | 속성                                                                |
| I-9  | 손님에게 보이는 view model에는 점수, 서랍 코드, 다른 서랍의 책이 없다                                                      | 타입 + 컴포넌트 테스트                                              |
| I-10 | 상태 문장의 조사(이/가, 을/를 …)는 서랍 이름의 받침에 맞는다                                                               | 속성(한글 음절 전체)                                                |
| I-11 | 공개 버전은 바뀌지 않는다. 손님 차례 도중 새 버전이 공개돼도 시작한 버전으로 끝까지 간다                                   | 저장소 계약 + 구조(시작 때 묶음을 받음)                             |
| I-12 | **별명은 서버로 가지 않는다.** 이벤트·요청 어디에도 별명, 이름, 연락처, IP, User-Agent가 저장되지 않는다                   | 타입(이벤트 스키마에 자리 없음) + API 테스트 + 속성(임의 추가 필드) |
| I-13 | 손님 차례가 끝나면(완료·시간 초과·처음으로) 별명, 답, 결과가 화면 상태에서 모두 사라진다. 다음 차례는 새 세션 ID다         | 예시 + 속성(상호작용열)                                             |
| I-14 | 한 차례의 이벤트는 퍼널 문법 순서를 따른다(ready → start → answer/back* → result → handover → book_view/purchase* → reset) | 속성(상호작용 무작위열)                                             |
| I-15 | 주인 확인은 잠금을 풀어야 열린다. 손님 화면에서는 다른 서랍의 정보를 볼 수 없다                                            | 컴포넌트 + API                                                      |
| I-16 | 응답과 정답 표시에는 어느 버전으로 답했는지가 함께 기록된다                                                                | 스키마(필수 필드)                                                   |

## 3. 아키텍처

### 3.1 함수형 코어, 명령형 셸

```
  routes/ (컨테이너: query·mutation·타이머를 컴포넌트에 연결. 분기 없음)
     │                                   │
  components/ (표시만: props in, 콜백 out)   queries.ts (query option 한곳)
                                         │
                                  api-client.ts (eden treaty) ── unwrap
                                         │  HTTP (타입은 App에서 추론)
  server/app.ts  createApp(deps)  ← 의존성 주입 팩토리
     │
  application/ (유스케이스: 포트를 받아 코어를 부르고 저장. 명령형 셸)
     │                    │
  domain/ (순수 코어)    persistence/ (포트 구현: memory · drizzle)
```

- **domain**은 React, elysia, drizzle, `Date.now`, `Math.random`을 import하지 않는다. 시각과 난수(표본 점검)는 인자로 받는다.
- **application**은 qr-quest처럼 유스케이스 함수(`publishQuestionSet(ctx, id)`)로 둔다.
- **server**는 HTTP 모양(경로, 상태 코드, 인증 매크로)만 안다.
- **persistence**는 포트 뒤에 숨고, 같은 계약 테스트를 메모리와 drizzle(PGlite)에 돌린다.
- **components**는 view model과 콜백만 받는다. **routes**는 연결만 한다(solo-quest 규칙).
- 손님 차례의 상태(별명, 답, 결과)는 라우트 한곳의 메모리 상태다. 코어의 `Turn` 값 하나로 표현하고, 처음으로 돌아가면 그 값을 버린다.

### 3.3 데이터 흐름

**손님 차례 (태블릿)**

1. 키오스크 첫 화면 loader가 `GET /api/kiosk/current`로 **공개 버전 묶음**을 받는다: 공개 버전(서랍 정의, 질문, 채점 방식, 문장) + 손님 화면에 필요한 서랍 속 책의 공개 필드.
2. 별명, 답, 채점, 순위, 문장은 **브라우저에서** 순수 함수로 계산한다. 별명은 서버로 가지 않는다(I-12). 와이파이가 흔들려도 차례는 끝까지 간다(EX-11).
3. 묶음은 차례가 시작될 때의 것을 쓴다(I-11). 처음 화면으로 돌아올 때 새 묶음이 있으면 바꿔 단다.
4. 이벤트는 큐에 쌓아 보내고, 실패하면 다시 보낸다. 이벤트 전송은 흐름을 막지 않는다.

**주인 확인 (같은 태블릿)**

5. 결과 화면의 주인 확인을 누르면 잠금(PIN)을 푼다. 서버가 PIN을 확인하고 짧은 주인 토큰을 준다 [확인 필요: PIN vs 주인 휴대폰].
6. 주인 확인 화면은 추천 서랍, 2순위 서랍, "비슷함" 표시, 서랍 속 책(수량)을 보여 준다. 열쇠 건넴과 산 책 기록은 주인 토큰으로 서버에 남는다.
7. 열쇠를 건네면 손님 화면은 서랍 속 책 안내로 넘어가고, 끝나면 처음으로.

**공개와 점검 (운영 화면)**

8. 관리자가 공개하면 서버가 같은 `analyze`를 다시 돈다. 점검과 서가 게이트를 통과해야 새 버전이 생긴다.

### 3.4 타입 안전한 끝에서 끝 연결

```
valibot 스키마 (domain)  ──►  elysia body/response 검증 (server)
        │                            │ typeof App
        ▼                            ▼
  타입 (v.InferOutput)      eden treaty (api-client) ─► unwrap ─► queryOptions ─► useSuspenseQuery
```

- 스키마는 한 번만 쓴다. 도메인 타입은 스키마에서 추론한다.
- 응답에도 스키마를 건다. API 테스트가 응답 모양을, 클라이언트 타입이 그 스키마를 따른다.
- 브라우저와 API 테스트가 같은 `createApiClient`를 쓴다(solo-quest).
- 이벤트 스키마에는 별명 자리가 **아예 없다.** 엄격 객체라 더한 필드는 거부된다. 이 두 가지가 I-12를 타입과 런타임 양쪽에서 막는다.

### 3.5 백엔드를 독립적으로 테스트한다

- `createApp(deps)`는 저장소 포트, 인증, 주인 잠금, 시각, id 생성기를 받는다.
- API 테스트는 메모리 저장소 + 고정 시각·id로 앱을 만들고 eden 클라이언트로 부른다. 파일·DB·포트를 모른다.
- 인증은 qr-quest처럼 better-auth를 주입하고, 테스트는 메모리 DB 위의 실제 better-auth로 로그인 쿠키를 얻는다.
- 프런트 없이 `api` 프로젝트만으로 손님 차례(묶음 → 이벤트), 주인 확인(잠금 → 건넴 → 산 책), 운영(책·서랍·질문 세트·공개) 시나리오를 HTTP 수준에서 끝까지 확인한다.

### 3.6 저장

| 대상                  | 저장                                                            | 이유                          |
| --------------------- | --------------------------------------------------------------- | ----------------------------- |
| 질문 세트 초안        | 행 하나 + 본문 jsonb                                            | 통째로 읽고 통째로 쓴다       |
| 공개 버전             | 버전 번호가 붙은 불변 행(jsonb, 학습 모델 포함), 공개 중 포인터 | I-11. 고치지 않고 새로 만든다 |
| 책, 서랍 속 책        | 정규 테이블                                                     | 목록·수량 수정이 잦다         |
| 퍼널 이벤트           | 추가 전용 테이블(허용 목록 열만)                                | I-12. 집계는 SQL              |
| 열쇠 건넴, 산 책      | 추가 전용 테이블(세션 ID, 버전, 서랍, 책)                       | 학습 데이터의 정답. I-16      |
| 운영자 계정, 주인 PIN | better-auth 테이블, PIN 해시                                    |                               |

개발·테스트는 PGlite, 운영은 postgres(drizzle).

### 3.7 남길 ADR 후보

1. 질문 세트는 초안과 불변 공개 버전으로 나누고, 본문(채점 방식·학습 모델 포함)을 JSON 문서로 저장한다.
2. 채점 방식은 공개 버전 안의 데이터다. v1 서랍별 문항 평균, v2 학습 모델이 같은 자리에 들어간다.
3. 손님 차례의 계산은 브라우저의 공유 순수 코어로 하고, 별명은 서버로 보내지 않는다. 공개 점검은 서버에서 같은 코어를 돌린다.
4. 퍼널 이벤트와 정답 표시는 허용 목록 스키마로만 받고, 차례마다 새로 만드는 세션 ID로만 묶는다.
5. 운영자 인증은 better-auth, 태블릿의 주인 확인은 PIN 잠금 + 짧은 토큰 [확인 필요].

### 4.3 공개 점검: 전수가 아니라 표본 + 쌓인 응답

문항형은 가능한 답이 너무 많다(5의 문항 수 제곱). `analyze`는 셋을 본다.

1. **표본:** 주입한 난수로 만든 무작위 응답 다수(시드 고정, 재현 가능). 결정 여부, 서랍별 1순위·1·2순위 비율(10~18%), 동점이 서랍 순서까지 간 비율.
2. **쌓인 응답:** 같은 질문들로 실제로 받은 답이 있으면 그것으로 다시 계산한 분포. 무작위 응답은 실제 사람과 다르게 답하므로(대개 4~5에 몰린다) 둘을 나란히 보인다.
3. **구조:** 서랍별 문항 수 균형, 비어 있는 서랍, 기준 응답 일치.

같은 함수를 ① 시드 질문 세트의 도메인 테스트, ② 관리자 공개 화면, ③ 서버의 공개 API가 함께 쓴다. 학습 모델(v2)의 비교도 같은 보고 모양 위에 "건넨 서랍과의 일치율"을 더한다.

## 5. UI / UX 설계

### 5.1 원칙

- **현장, 태블릿, 서서 또는 앉아서.** 손님은 예약하고 온 사람이다. 서두르지 않지만 뒤에 다음 손님이 있을 수 있다. 문항 하나에 몇 초, 전체 3분 안팎.
- **한 화면, 한 목적.** 화면마다 "지금 할 행동"은 하나다. 강조 요소가 둘이면 하나를 내린다.
- **팔 길이에서 읽힌다.** 태블릿은 받침대 위에 있다. 글자는 휴대폰보다 크게, 누름판은 손가락 끝이 아니라 손가락 마디 크기로. 세로·가로 모두에서 질문 화면은 스크롤이 없다.
- **문장이 주인공.** 큐레이터의 문장은 명조 계열·넉넉한 행간으로, 조작 UI는 고딕으로 작게.
- **규정하지 않는다.** "○○형", 점수, 순위 숫자, 퍼센트, 서랍 코드는 손님 화면 어디에도 없다(I-9). 2순위는 "함께 필요한 것"처럼 부드럽게.
- **서랍을 여는 순간을 아낀다.** 결과 화면은 서랍 속 책을 미리 보여 주지 않는다 [확인 필요]. 책 이야기는 열쇠를 받은 뒤에.
- **다음 손님을 위한 화면.** 끝나면 처음 화면으로 돌아가고, 앞 사람의 흔적이 없다. 이 전환은 손님이 안심할 수 있게 보이도록 한다("토끼 님의 기록은 남지 않아요").
- **조용한 브랜드.** 책방79-1의 종이·잉크 느낌을 앱 테마(Panda 토큰 확장)로. 장식보다 여백.

### 5.2 흐름

```
[첫 화면: 별명] ─시작─► [질문 1] ─► … ─► [질문 n] ─► [결과]
                          ▲  │ 되돌아가기                │ "주인에게 보여 주세요"
                          └──┘                          ▼
                                              [주인 확인 (잠금)] ── 건넬 서랍 · 서랍 속 책 · 비슷함
                                                        │ 열쇠 건넴
                                                        ▼
                                              [서랍 속 책 안내] ── (주인) 산 책 기록
                                                        │
                       ◄──────── 처음으로 (완료 · 유휴 시간 초과 · 직접) ─────┘
```

- 문항형은 다섯 칸 척도("전혀 아니다 ··· 매우 그렇다")를 가로로 크게 놓는다. 누르면 곧바로 다음 문항("다음" 버튼 없음). 되돌아가기는 늘 같은 자리.
- 진행은 "n / 전체"를 조용히 보여 준다. 문항형은 문항 수가 정해져 있어 약속할 수 있다. 선택형 분기가 섞이면 "n번째 질문"만.
- 유휴 시간 초과 전에 "계속하시겠어요?"를 한 번 묻는다. 결과 화면과 주인 확인 화면은 시간 초과를 길게 둔다 [탐색].

| 운영: 서가      | 빠르게 많이 등록                         | 책 목록                   | 표 + 편집 다이얼로그, 관련도 0~5 일곱 칸                                                                                                                                            | 데스크톱 또는 태블릿 가로                                                             |
| 운영: 서랍      | 서랍마다 무엇이 몇 권                    | 서랍 일곱 칸              | 서랍별 책과 수량, 3종 미만 경고                                                                                                                                                     | 서랍 7개를 실제 서랍장처럼 격자로 [탐색]                                              |
| 운영: 질문 세트 | 서랍마다 문항을 쓰고 균형을 본다         | 공개 전 점검 보고         | 서랍별 문항 목록(문항 수가 한눈에), 문항 미리보기(태블릿 모양), 상태 문장 미리보기(조사·별명), 기준 응답, 점검 보고(분포 막대, 표본/실제 나란히), 공개 버튼은 통과 때만             |                                                                                       |

## 8. 구현 순서

```
00001 뼈대·테스트 단계·fast-check·CONTEXT/ADR
  └► 00002 코어: 질문 세트·손님 차례·채점(item-mean)·순위
        ├► 00003 공개 점검기 + 시드 질문 세트(문항) [탐색 섞임]
        ├► 00004 상태 문장·조사·별명·인용
        └► 00005 서가: 책·서랍 속 책·게이트·저장소
              └► 00006 묶음 API + 별명 화면·질문 화면·처음으로
                    ├► 00007 결과 화면
                    │     └► 00012 주인 확인·열쇠 건넴·서랍 속 책 안내 (00009 필요)
                    └► 00008 익명 퍼널 이벤트·정답 표시
00009 운영자 인증·주인 잠금 (00001 뒤 언제든)
  ├► 00010 큐레이터: 책·서랍 채우기 (00005 필요)
  └► 00011 관리자: 질문 세트 편집·점검·공개 (00003, 00004 필요)
00013 [v2·탐색] 학습 데이터 내보내기, 학습 모델 채점 방식, v1과 비교 (00008, 00011, 00012 뒤)
```

1~8 + 12까지 끝나면 시드 데이터로 책방에서 손님 차례 전체가 돈다(운영 화면 없이 시드로 오픈 가능).
9~11이 끝나면 책방이 개발자 없이 책, 서랍, 문항을 바꾼다. 13은 50~100건이 쌓인 뒤 시작한다.

각 티켓은 solo-quest 방식을 따른다: 인수 조건이 곧 TDD 체크리스트, 한 동작씩 빨간 테스트부터, 구조 변경과 동작 변경은 다른 커밋, 끝나면 "작업하며 배운 것"을 적는다.
