# TICKET-00013 준비: 데이터가 쌓인 뒤 시작할 것

TICKET-00013은 v2 탐색이다. 지금은 실제 손님 응답이 없어 시작하지 않는다. 이 문서는
데이터가 쌓였을 때 바로 움직이기 위한 선행 조건과 순서다. 결정은 책방 주인과 함께 한다.

## 1. 시작 조건

- [ ] `result_view`, `handover`, `purchase_record`가 실제 손님 차례로 **50~100건** 쌓였다.
- [ ] 각 차례에 `version`과 익명 `sessionId`가 있고, `result_view`의 답 길이/형식이 그
      버전의 질문과 맞는다. (TICKET-00011의 점검 보고가 이미 다른 버전 답을 거른다.)
- [ ] 주인이 “추천과 다르게 건넨” 차례를 최소 10건 이상 직접 확인했다(R-7). 그래야
      학습 모델이 v1 추천을 따라 하기만 하는지 볼 수 있다.
- [ ] 주인이 학습 데이터 사용 범위(익명, 버전, 답, 추천/건넨 서랍, 산 책의 서랍)를
      승인했다. 별명·연락처·IP는 내보내지 않는다.

## 2. 내보내기 (아직 만들지 않음)

한 행은 **한 차례**다. `sessionId`로 `result_view`와 `handover`, `purchase`를 잇는다.

| 필드             | 출처                                                |
| ---------------- | --------------------------------------------------- |
| version          | result_view.version (handover/purchase와 같아야 함) |
| answers          | result_view.answers                                 |
| recommended      | result_view.ranking.first                           |
| handed           | handover.handed (없으면 null)                       |
| purchasedDrawers | purchase.drawer 목록 (없으면 빈 배열)               |
| scores           | result_view.scores (서랍별 점수·5의 수)             |

- 같은 세션에 handover가 여러 번 있으면 마지막 handover를 정답으로 쓰고, 그 사실을
  행에 남긴다. purchase는 여러 개일 수 있다.
- 내보내기 파일에는 위 필드만 쓴다. `kioskName`, `sessionId`도 학습 입력에는 쓰지 않고,
  디버깅용으로만 남긴다. 별명은 애초에 이벤트에 없다.
- 권장: `bun run export:training` 같은 앱 밖 스크립트가 JSON/CSV를 만들고, 운영자가
  내려받는다. 앱 안에 학습 버튼을 만들지 않는다.

## 3. 학습/평가 분리

- 행 단위가 아니라 **세션 단위**로 train/eval을 나눈다. 같은 손님의 답이 양쪽에 섞이면
  과대평가된다.
- 시간 순서가 있으면 최근 20%를 eval로 두는 편이 실제 배포와 비슷하다.
- eval에는 “추천과 다르게 건넨” 차례를 가능한 한 많이 넣는다. 그래야 v1 베끼기를 본다.
- 표본이 50건이면 eval 10건 남짓이다. 지표의 신뢰구간을 함께 적고, 100건 전에는
  채택을 서두르지 않는다.

## 4. 모델과 비교

- 모델: 사람이 읽을 수 있는 의사결정 나무. 공개 버전 JSON에 나무·버전·특징 순서를
  불변 데이터로 넣는다. `learned` 채점기는 같은 `DrawerScores`를 낸다(I-6).
- 비교 지표:
  1. 건넨 서랍과의 일치율 (v1 vs learned)
  2. “추천과 다르게 건넨” 차례에서의 일치율
  3. 서랍별 추천 분포와 쏠림 (기존 공개 점검과 같은 표)
  4. 문항 수가 다른 버전에서도 점수가 정해지는지(I-1/I-5)
- 채택 기준(초안): held-out 일치율이 v1보다 높고, “다르게 건넨”에서도 v1보다 낫고,
  분포가 10~18%를 크게 벗어나지 않는다. 하나라도 무너지면 **보류**한다.
- 결과가 v1과 비슷하거나 나쁘면 채택하지 않는 것이 정상적인 결론이다.

## 5. 공개 전 점검

- learned 모델도 `analyze`와 `checkShelfGate`를 통과해야 새 버전으로 공개한다.
- 같은 버전·같은 답이면 같은 순위(I-2), 순위 이후 계산은 v1과 같다(I-6).
- 관리자 화면에서 나무 규칙을 문장으로 읽고, “이 규칙이 손님을 규정하지 않는지”를
  주인이 확인한다. 필요하면 [탐색]으로 규칙 미리보기 화면을 만든다.

## 6. 결론을 남길 곳

- 채택/보류와 이유를 `docs/adr/`에 ADR로 남긴다.
- 데이터 건수, train/eval 분리, 지표, 실패한 지표, 주인 확인 내용을 함께 적는다.
- 보류하면 다음 데이터가 더 쌓일 때 다시 볼 조건(예: 100건, “다르게 건넨” 20건)을
  적는다.
