# TICKET-00003: 공개 점검기와 시드 질문 세트(문항)

- 스펙: [TECH_SPEC](TECH_SPEC.md) §4.3, R-1, R-2, R-3, PRD 부록 A-3
- Blocked by: TICKET-00002
- Status: done

## 만들 것

- `analyze(set, rng, recorded?)` → `SetReport`:
  - 표본: 주입한 난수(시드 고정)로 만든 무작위 응답으로 결정 여부, 서랍별 1순위·1·2순위 비율, 서랍 순서까지 간 동점 비율, "비슷함" 비율.
  - 쌓인 응답: 넘겨받은 실제 답 목록이 있으면 같은 지표를 나란히.
  - 구조: 서랍별 문항 수 균형, 문항 없는 서랍, 기준 응답 일치.
- 기준 응답(`BaselineAnswers`)을 질문 세트에 함께 저장한다. 서윤의 응답이 첫 기준 응답이다.
- MVP 시드 질문 세트: 서랍 7개 × 문항 2개(문항형, `item-mean`).

## 알아야 할 것

- 이 티켓은 **탐색이 섞여 있다.** 문항 문장은 v0.2 질문과 선택지(PRD 부록 A-5)를 출발 자료로 쓰되, 최종 문구는 책방 주인 선생님과 함께 정한다.
  코드가 기다리지 않도록 [가정] 문구로 시드를 만들고, 문구만 바꾸는 후속 커밋을 둔다.
- 무작위 응답은 실제 사람과 다르게 답한다(R-3). 표본 결과로 기준을 몰래 느슨하게 하지 않는다. 표본 기준을 넘지 못하면 그 사실을 보고서와 함께 남긴다.
- 점검기는 TICKET-00011의 공개 화면·공개 API, TICKET-00013의 학습 모델 비교가 그대로 쓴다. 보고 모양을 화면에서 쓰기 좋게 둔다.

## 작업하며 배운 것

- 기준 응답은 질문 세트 안에서 답 개수·형식까지 파싱한다. `answerValueFor`를
  `QuestionSetSchema`의 검사에서 쓰면 "이 답이 이 질문에 맞는가"를 채점기와 같은
  규칙으로 확인한다. `answer.ts`가 `question-set.ts`를 타입으로만 import하므로
  런타임 순환은 없다.
- `baselines`는 `v.optional(..., [])`로 없으면 빈 배열이 된다. 그래서 DTO는 늘
  `baselines`를 내고, 기존 질문 세트도 왕복이 같다. 새 필드를 optional로 두되 출력은
  한 모양으로 정규화한 쪽이 소비자 분기가 줄었다.
- 표본 4,000개, 시드 79에서 시드는 통과했다. 다만 7서랍·2문항에서 서랍 순서가
  첫 번째인 서랍은 구조적으로 1순위가 18.04%까지 나온다(정확 계산). 표본은 17.9%로
  상한 안이지만 여유가 작다. 문항을 3개로 늘리거나 기준을 바꾸는 일은 주인과 정한다.
- 문항이 0개인 서랍은 실패, 문항 수가 다르기만 한 것은 경고로 나눴다. 빈 서랍은
  그 서랍이 사실상 추천될 수 없다는 뜻이고, 수 불균형은 PRD가 "경고"라고 적었기
  때문이다.
- 쌓인 응답의 쏠림은 지금 경고다. 표본이 공개 게이트를 맡고, R-3은 50~100건이
  쌓인 뒤 실제 분포를 기준으로 보라고 한다. 그 전에 소량 응답으로 공개를 막으면
  데이터가 쌓이기 전까지 아무것도 공개할 수 없다.
- 표본 생성기는 문항형뿐 아니라 선택형도 답한다. 시드는 문항형만 쓰지만 TICKET-00013의
  학습 모델 비교와 점검기의 건전성 속성이 같은 함수를 쓰기 때문이다.
- 쌓인 응답은 부분 답을 허용한다. 채점·순위는 기존 코어가 하므로 답이 짧으면
  나머지 서랍은 "증거 없음 = 0"으로 남고, 순위는 그래도 정해진다.
