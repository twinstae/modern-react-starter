# TICKET-00005: 서가 — 책, 서랍 속 책, 게이트, 저장소

- 스펙: [TECH_SPEC](TECH_SPEC.md) §2.1, I-7, I-9, R-9, §3.6
- Blocked by: TICKET-00002
- Status: todo

## 만들 것

- 도메인: `Book`(제목, 저자, 서랍별 관련도 0~5, 핵심 단어, 권하는 이유, 함께 생각해 볼 질문), `DrawerStock`(서랍 코드별 책과 수량), 서랍 표시(번호·열쇠).
- `checkShelfGate(stock)`: 서랍마다 수량 1 이상인 책이 3종 이상인지, 부족한 서랍을 돌려준다.
- `ownerView(curation, stock, books)`: 주인 확인 view model — 추천 서랍, 2순위 서랍, 비슷함, 각 서랍의 책과 수량, 게이트 경고.
- `drawerBooksView(drawer, stock, books)`: 손님에게 보이는 서랍 속 책 안내 view model(건넨 서랍의 책만).
- 저장소 포트와 구현: 책, 서랍 속 책. 메모리 구현과 drizzle(PGlite) 구현에 같은 계약 테스트.

## 알아야 할 것

- 서랍의 이름과 문장은 질문 세트에, 서랍 속 책은 서가에 있다. 둘은 서랍 코드로만 만난다.
- 관련도는 저장하고 보여 주지만 추천에 쓰지 않는다(PRD 결정).
- 수량은 실제와 어긋날 수 있다(R-9). 수량 0인 책도 목록에서 사라지지 않고 "없음"으로 보이며, 서비스를 멈추지 않는다.
- 손님용 view model에는 건넨 서랍의 책만 있다. 다른 서랍의 책은 주인 view model에만 있다(I-9, I-15).

## 인수 조건

- [x] 게이트가 서랍마다 3종 이상인지 보고 부족한 서랍을 이름과 함께 돌려준다(예시).
- [x] 주인 view model에 추천·2순위 서랍과 각 서랍의 책·수량, 3종 미만 경고가 담긴다(예시).
- [x] 무작위 서가와 순위에서 손님용 view model에는 건넨 서랍이 아닌 서랍의 책이 없다(속성, I-9).
- [x] 책·서랍 속 책 저장소 계약 테스트가 메모리와 PGlite 구현 모두에서 통과한다.

## 작업하며 배운 것

- 서랍 표시(`mark`)는 `statement`처럼 optional + nullable로 받고, 파싱·DTO에서 `null`로
  정규화한다. 시드에는 `[가정]` 표시를 넣었다. 소비자는 필드 존재 여부를 묻지 않는다.
- 관련도는 서랍 일곱 키를 모두 가진 strict object다. `v.record`는 빠진 키를 잡지 못해
  "모든 서랍"을 타입으로 보장하지 못했다. JSONB에는 `$type<BookRelevance>`로 저장한다.
- 게이트는 `(서랍, 책)` 줄 수가 아니라 **수량 1 이상인 서로 다른 책 id 수**를 센다.
  수량 0인 책은 게이트에서 빠지지만 목록에서는 "없음"으로 남는다(R-9).
- 서랍 이름은 게이트와 주인 view model에 질문 세트에서 인자로 들어간다. 서가 저장소에는
  코드만 있고 이름이 없다. 손님 view model은 서랍 코드·관련도·점수 없이 책 다섯 필드만
  가진 타입이라 I-9를 타입으로 막는다.
- 서랍 속 책이 서가에 없는 책을 가리키면 `MissingBookError`로 멈춘다. 반쪽 책을 보이지
  않는다. PGlite에는 외래 키를 걸지 않아 이 불일치를 도메인에서 확인할 수 있다.
- 포트는 `application/shelf-ports.ts`에 두고, 계약 테스트는 `*.test.ts`가 아닌
  `shelf-store.contract.ts`에 두어 메모리와 PGlite 테스트가 같은 `describe`를 부른다.
  PGlite는 파일 하나에 DB 하나만 열고, 각 테스트 앞에서 두 표를 비운다.
- 목록 순서는 메모리도 SQL과 같게 책 id, 서랍 코드 → 책 id로 정렬한다. 계약 테스트가
  구현 차이를 순서 차이로 오해하지 않는다.
